# Proposal: opt-in cron delivery windows (not implemented)

Status: design plus opt-in storage primitives for review. The existing bounded, expiring `not_before` queue now has a separate per-target receipt table, but no setting, CLI switch, tool argument or scheduler call site opts into a quiet window. Cron delivery and job execution remain unchanged by default. Do **not** advertise quiet windows as available to users from this draft.

## Why this is different from active hours

A nightly job should still finish its work and save its result, without a 03:00 human notification. Heartbeat active hours (#93161) skip *execution* and do not preserve each result. Silence/notification toggles suppress output rather than release it later. This design proposes deferring only a human-facing notification, retaining each result separately. Webhooks, automation, Bot Chat and machine recipients should not inherit a human policy.

Issue #17459 rejects hidden/default control-plane quiet-hour suppression. An opt-in owner-configured *safety policy*, with explicit agent/operator-visible `queued_until`/terminal feedback, is the only candidate discussed here. The agent cannot set an `urgent` flag or override the policy from a prompt. The scheduler must continue execution and approval decisions unchanged. **Maintainer decision requested before wiring any delivery gate.** An advisory-only alternative consistent with #17459 is described below.

## Proposed opt-in contract (future PR, subject to maintainer approval)

- Per-job or profile owner setting, default absent: `cron.delivery_window: {start: '22:00', end: '07:00', timezone: 'America/New_York'}`. Name and placement are provisional, **not implemented config**. Owner-supplied IANA timezone is mandatory and validated with `zoneinfo.ZoneInfo` at the config/write boundary; never infer host or sender timezone. Reject equal, invalid or missing bounds and unknown zones; never turn invalid input into a silent always-on window. Allow only human-directed explicit recipients; reject mixed/ambiguous target expansion rather than partially delivering a batch and calling it delivered.
- Start-inclusive/end-exclusive local quiet interval. A daytime interval uses `start <= local_time < end`; an overnight interval uses `local_time >= start or local_time < end`. Convert each candidate instant from UTC into the named zone *before* comparing local clock fields. At a nonexistent spring-forward wall time no instant exists; release at the first eligible real instant. At a repeated fall-back wall time both folds are quiet or both eligible by the same local-time predicate. Reevaluate eligibility in the gateway when claiming, not just once when enqueued, because DST or owner configuration can change before release.
- Persist the sanitized payload, resolved destination identity, failure/result category and original execution ID before worker completion; one durable record **per target**, not the current one-row-per-execution aggregate. Keep an at-most-once claim with `unknown` after a crash mid-send. `queued` is not `delivered`; only a confirmed send yields `delivered`. A transport with no evidence remains unverified, not confidently sent. Do not call an unresolved destination delivered. The same receipt must survive restart without rerunning the agent. Emit agent/operator-visible queued, released, expired and failed states via existing ledger/cron status, without creating another agent turn or LLM call.
- On pause or delete, the owner may choose explicitly to cancel pending notifications (terminal `suppressed`, not `delivered`); until that UX exists, do not wire the feature. A changed timezone/window should apply to pending records only via an explicit documented policy (proposed: snapshot the policy at enqueue; owner may cancel or requeue, never silently retarget). A delivery destination is snapshotted and never recomputed from current home channels. Failure notices follow the same opt-in policy only when they are ordinary cron notification targets; approval requests and security/transport incidents must not be quietly held by an unrelated job policy.
- No forced digest/coalescing or automatic urgent bypass. Propose a finite age limit (e.g. 48 hours) and bounded row/byte quota per profile; capacity rejection is visible, never a silent eviction. Expiry is terminal failed with redacted payload and an inspectable error, not an automatic out-of-window send. Encrypted-at-rest guarantees are not supplied by the existing SQLite store; it is profile-local and permission-restricted, and notification payloads may contain sensitive text. Document the exposure before enabling it.

## Tested building blocks in this draft

`cron.delivery_queue.enqueue(..., not_before=<aware instant>, expires_at=<aware instant>)` stores a UTC release and expiry on the existing at-most-once receipt. The gateway's `drain` only claims eligible unexpired receipts and terminalizes expired unclaimed receipts as failed, redacting terminal payload and writing back the ledger outcome. The existing `get_status` exposes a pending receipt with its release instant. At most 100 explicitly deferred pending rows and 64 KiB content per row are admitted; a full queue raises a visible error, not eviction. Existing immediate enqueues use null columns and are unchanged. The existing 1,000-row terminal retention/tombstones preserve idempotency. This primitive is deliberately **not connected** to the job scheduler or exposed as a user setting: its `job_json` still contains an aggregate job, not an immutable, normalized per-target destination.

`cron.target_receipts.enqueue_targets` provides an atomic batch of concrete, destination-snapshotted receipts in the same profile-local database. `release_targets` requires an explicit per-target send result (`delivered`, `failed`, or `unknown`), distinguishes human and machine kinds, checks current job state (paused rows wait; deleted rows are suppressed), expires unattempted rows and fences abandoned claimed sends as `unknown` without replay. `get_target_receipts` exposes each status; neither these rows nor the aggregate queue are called by a quiet-window setting today. The caller must classify target kind, resolve platform/chat/thread and supply an aware UTC-equivalent release/expiry; it must not pass routing aliases or assume an adapter's ambiguous result is confirmed. The batch cap is 32 targets, 100 pending/in-flight rows per profile, 64 KiB content per receipt, an 8 KiB target snapshot and a seven-day release-to-expiry span. Terminal content/snapshots are cleared; at most 1,000 full terminal rows survive, with at most 10,000 tombstones retained for up to 30 days (idempotency is bounded to that age/count horizon, not forever). The existing SQLite permission policy protects the file; this is not encryption at rest. A full disk or corrupt database fails the write rather than silently dropping the obligation; a post-send write failure is fenced `unknown` on the next recovery, never resent.

To reproduce on a fresh checkout with an isolated test interpreter, run `HERMES_PYTHON=/path/to/test-venv/bin/python scripts/run_tests.sh tests/cron/test_delivery_queue_not_before.py tests/cron/test_delivery_queue.py tests/cron/test_target_receipts.py`. Tests use tmp_path and fixed UTC clocks, covering duplicate drains, expiry, capacity, spring/fall instants, microsecond boundaries, migration, multi-target outcomes, changed destination, pause/delete, profile isolation and immediate compatibility. No credentials or gateway restart are needed.

## Unfinished acceptance criteria / alternative

The required target-type classification at the routing boundary, owner-only validated config and CLI/UI write path, operator-visible feedback (beyond the storage API), scheduler dispatch/release wiring, changed-policy semantics, approval isolation, and end-to-end gateway/restart tests remain **unimplemented**. Current `_deliver_result` still resolves targets as a batch and sometimes runs inline; its legacy aggregate queue is not replaced by the per-target table. Simply delaying that aggregate row would retarget on changed config, hold machine recipients and misreport mixed successes; it is not safe. A future implementation must test the actual consumer before enabling quiet delivery. If maintainers prefer #17459's advisory-only policy, expose local time/window in cron tool results and let the owner schedule notifications explicitly instead of installing an automatic delivery gate. The draft can be closed without activating a conflicting policy.
