# Native task reply receipt v1 — source candidate, not registered

Status: source-only transaction primitive in `hermes_cli/native_task_replies.py`; no HTTP route, broker grant, owner issuer, running-runtime change, deployment, or MC adoption. Canonical C1 remains `t_7da54954`. This module must not be presented as an authenticated public reply API.

## Preconditions for a trusted native bridge

- The source resolver authenticates installation, current owner and owner incarnation, profile, and thread/target binding on every request, including reconciliation. It supplies `ReplyScope` server-side only. No browser, producer body, display label, tenant, task assignee or notification subscription may assert owner authority. Absent resolver fails closed.
- The trusted bridge opens an explicit pinned, existing board DB from the installation's canonical board registry and independently supplies `canonical_board`. Never use `HERMES_KANBAN_DB`, current-board pointer, browser pathname or `board=None` as proof. The caller must verify the physical DB and board metadata at request time; a slug alone is not a DB attestation. Another worker owns the occurrence/context issuer; this module does not mint owner binding.
- Before issuing `task_generation`, call `install_schema` against the real board and authorize the task/board/current owner. `current_generation` creates an opaque 128-bit generation and a deletion trigger tombstones it on task deletion. The generation is source state, not `created_at` or SQLite rowid. The source must deny stale context after owner reassignment, profile change or board recreation. Board recreation requires an independent board incarnation in the caller's attested namespace; this module by itself cannot detect a replaced board DB.
- Bridge accepts only UTF-8 `body` (1–16,384 bytes), nonnegative `expected_revision`, and bounded `idempotency_key`. Request identity is installation + owner_incarnation + thread_id + expected_revision + key + SHA-256 of exact UTF-8 bytes. Scope also binds owner, profile, board, task, generation. Whitespace is preserved. The browser sends no scope, authority, path or proof fields. CSRF/Origin and `account.communications.reply` plus underlying native capability remain MC-side gates.

## Atomic operation and receipts

`reply(conn, scope=…, expected_revision=…, idempotency_key=…, body=…, canonical_board=…, authorize=…)` begins `BEGIN IMMEDIATE`, rechecks task generation and assignee/profile and calls a mandatory CURRENT owner-authorize resolver, then looks up the durable receipt. Identical retry returns the same `ReplyReceipt(native_namespace, target_kind='task', target_id, target_generation, native_reply_id, native_revision, idempotency_key)` even after a different comment advances revision. Changed exact bytes, scope/key/revision collision, stale revision or recreated task conflicts. The comment, task event and receipt commit together; failure rolls all back. Unknown response after dispatch must be reconciled using this exact key/body, not sent through generic `kanban_db.add_comment` or `/api/kanban/tasks/:id/comments` again.

`native_revision` is the current task's maximum comment row ID; generic native comment writers advance it. Native comment deletion/pruning is not currently a supported operation under this revision contract; a future deletion writer must introduce a monotonic per-task revision rather than allow rollback. Receipt IDs are valid only within the attested board namespace and generation.

Errors for adapter mapping: `ReplyConflict` -> 409; `ReplyUnauthorized` -> 403 (or 503 if the trusted owner resolver is unavailable); invalid input -> 400, oversized UTF-8 -> 413; SQLite write error -> 503/unknown and reconcile by exact request. The native module does not implement HTTP status mapping. `/api/hermes/approvals/resolve` remains the sole decision route; a task comment or receipt does not approve anything.

## Outstanding adoption gate

An authenticated native owner/board issuer, explicit board DB open/identity verification, and source-to-MC broker wire/capability still need integration and independent exact-head review. No producer can invoke this primitive safely merely by passing a callback that returns `True`. Until then, MC's communication reply stays `501 native_reply_unavailable`; the old comment path remains non-idempotent. This is not signed-in, live, Telegram, or customer evidence.
